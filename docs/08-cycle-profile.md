# Cortrace — 周期精确的性能剖析（`cortrace profile`）
日期：2026-10-30
状态：已实现并上板验证（STM32H743 + NuttX，缓存开/关对照）。
> 关系：直接吃 `00-architecture.md` 的 `Element` 流，和覆盖率（`07-realtime-coverage.md`）共用抓取、去帧和 OpenCSD 解码，
> 只多一个消费者 `Profiler`（`src/profile.cpp`）。不动调用栈和 Perfetto 输出。
---
## 1. 能得到什么
ETM 打开周期计数（`TRCCONFIGR.CCI`）后，每隔几个周期就报告一次"距上次报告过了多少个 CPU 周期"。
它和指令流在同一个数据流里，所以不用插桩就能得到：

| 结果 | 含义 |
|---|---|
| 每个函数的自身周期、CPI | 热点在哪，哪些函数的 CPI 高（有停顿） |
| 每个异常的入口周期和运行周期（p50、p90、p99、max） | 中断开销，抖动 |
| 周期性异常（SysTick）的晚到量，和它在等什么 | 中断延迟抖动，关中断区间的实测长度 |
| 单独成段的基本块，每次运行的周期分布 | 同一段代码时快时慢，差值就是缓存和 Flash 的停顿 |
| 周期时钟与全局时间戳的偏差（ppm） | 这份数据本身可不可信 |
| 每个函数的访存额外周期（LSU%）、CPU 占用率（SLEEP）、异常开销落在哪（EXC） | 停顿是访存还是别的；需要打开 DWT 事件计数器，见 §7 |

**得不到什么。** M7 的 ETM 没有数据 trace（`TRCIDR0.TRCDATA=0`），也没有 PMU，所以看不到 cache miss 的次数，
也看不到某次访存的延迟。停顿只表现为周期数；DWT 的 LSU 计数器能把访存停顿单独分出来（§7），
I-cache 和 Flash 的取指停顿仍要靠对照实验（§5）。
---
## 2. 周期怎么归到代码上
流里的顺序是 `[指令段…, 周期计数, 异常, 周期计数, 异常的指令段…]`。一个周期计数是"距上一个计数的周期数"，
所以它覆盖的是**它之前**、上一个计数之后的那些指令段（一个"窗口"）。

- 窗口里只有一个指令段：这些周期全是它的，精确。
- 窗口里有几个指令段：按指令数分摊。相互调用很频繁的相邻函数，单个看有一个窗口的归属误差，成组看不受影响。
- 窗口里没有指令段（异常入口、trace 丢失之后）：记入 `no_instr_cycles`，报告里给出占比。
- 周期计数的分辨率由阈值决定（`TRCCCCTLR`，默认 16 个周期），所以分不出单条指令。
- **时间戳包里带的周期数不能再加。** 单靠周期计数包得到的时钟已经和全局时间戳吻合到几个 ppm；把时间戳包的周期数也加上，
  时钟会多算约 1%，SysTick 间隔偏 14,000 个周期。
- 归属方向是上板验证出来的：关掉缓存后，一个窗口的周期数和它自己的指令数相关（r=0.46，0.33），
  和上一个窗口的相关性低得多（0.34，−0.01）。

异常的入口周期是异常元素之后的第一个周期计数（硬件压栈、取向量、到第一个周期点）。运行周期是入口之后的第一个计数，到返回之后的第一个计数。
周期性异常的晚到量以"一段不间断 trace 里最早的一次"为零点，按 `period` 的格子算：压栈和取向量这类固定开销不在里面。
trace 一旦丢数据（失步、溢出、重新开始），就换一段，不跨段比较。

## 3. 用法
抓取之前要用带周期计数的 profile 布防：

```sh
cortrace arm --platform stm32h743 --os none --profile timing --probe-telnet 127.0.0.1:4444
cortrace profile run --elf fw.elf --out-dir ~/traces --iface enx0123 --secs 3 \
    --sysclk-hz 150e6 --tsgen-hz 75e6
cortrace profile report ~/traces/prof_<tag>.json --top 40
cortrace profile diff base.json other.json          # 两次实验对比（B/A）
```

- 抓取是原始数据落盘（约 75 MB/s），处理速度约每抓 1 秒花 6 秒（单线程，指令流有顺序依赖）。超过 5 秒要 `--allow-long`。
- 抓取丢了 UDP 帧就直接失败：周期时钟要求每个计数都在。
- `--sysclk-hz` 和 `--tsgen-hz` 都给了才会做时钟自检；不给也能出结果。
- `--period-exception N`（默认 15，SysTick）、`--period-cycles`（默认取间隔的中位数）。
- 底层工具 `cortrace-prof --raw-in raw.bin --elf fw.elf --syms fw.nm --out prof.json`，按 1 MiB 流式读取，内存与文件大小无关。
- 输出文件是 JSON（`format: cortrace-prof`，`version: 1`），报告命令只是它的文本视图。

## 4. 验证（STM32H743 @ 150 MHz，NuttX，I/D cache 开，D-cache 写通）
| 检查 | 结果 |
|---|---|
| 周期时钟对全局时间戳（3 s） | 偏差 −0.0 到 +8.7 ppm（6 次抓取） |
| SysTick 间隔对真值 1,500,000 周期 | 中位数偏差 0 到 2 个周期 |
| 重复抓取的一致性 | CPI 1.469 / 1.468，指令数相差 < 0.02% |
| 关 `TRCSTALLCTLR`（FIFO 满时是否拖住 CPU） | 指令数、CPI 逐项相同，没有反压 |
| 各函数自身周期之和 + 无指令周期 | 等于周期总数 |

**SysTick 抖动的原因找到了。** 300 个 tick 里 47 个晚到超过 1000 个周期，最大约 3500 个周期（23 µs）。
它们全部发生在 `nxsched_set_running_priority` 提高 BASEPRI 的区间：这个函数每次实测 2854 到 3786 个周期，
3 秒里被调用约 29,000 次，占 22% 的时间；tick 落进去的比例是 24.7%。晚到量在 0 到 3500 之间均匀分布，符合"挂起、等解除屏蔽"。

**缓存对照**（同一个固件，同样 3 秒，运行时改 `SCB_CCR` 的 IC、DC 位）：

| 配置 | CPI | SVCall 运行周期 | 说明 |
|---|---|---|---|
| I+D 开 | 1.47 | 371 到 573，p50 451 | 同一条路径波动 200 周期，是命中和未命中的混合 |
| 关 I-cache | 5.18 | 1009 到 1017 | 几乎没有波动：纯 Flash 取指 |
| 再关 D-cache | 7.00 | 1403 到 1477 | |

组合函数的 CPI（缓存开 / 关 I / 再关 D）：`compute_step+compute_mix+worker_compute` 1.09 / 4.77 / 7.35，
`memcpy+worker_fileio` 0.67 / 7.58 / 7.84。热点基本块的单次周期有分布（如 `nxrmutex_lock` 的一个块 29 到 73 个周期），
这就是 miss 在 trace 里的样子。

## 5. 怎么判断停顿的来源
trace 只给周期，不给原因。做法是只改一个条件，跑两次，用 `profile diff` 对比 CPI 和异常运行周期：

- 关 I-cache：`mww 0xE000ED14 <SCB_CCR & ~0x20000>`，再关 D-cache 用 `~0x30000`。D-cache 写通时关掉是安全的。
  恢复要先让缓存失效，最省事的是复位目标。
- 不同的 Flash 等待周期、不同的主频，同理。
- 对比时看 CPI，不看占比：慢的配置单位时间里跑的指令少。

## 6. 局限
- 周期精度受阈值限制（16 周期）。调低 `TRCCCCTLR` 会更细，但 ETM 数据量会涨。
- 单线程处理，约 6 倍于抓取时长。
- 只有"单独成段"的基本块有精确周期；缓存全开时这类块很少（约 200 个），关缓存后更多（400 到 520 个）。
- 周期性异常的零点是"最早的一次"，所以报告的是相对晚到量，不含固定的入口延迟。
- 看不到 DMA、总线争用本身，只看到它们造成的停顿。

## 7. DWT 事件计数器（LSU、CPI、FOLD、EXC、SLEEP）
DWT 有 5 个 8 位计数器，计数器每绕一圈就在 ITM/DWT 流（TPIU stream 1，和 ETM 同一个口）里发一个事件包，
一个包代表 256 次事件：

| 计数器 | 数的是 | 用处 |
|---|---|---|
| LSU | 访存指令多花的周期 | 把访存停顿（D-cache、总线、外设）和取指停顿分开 |
| EXC | 异常入口、出口的开销周期 | 中断的压栈、出栈开销落在谁身上 |
| SLEEP | 睡眠（WFI）的周期 | CPU 占用率 |
| FOLD | 被折叠（零周期）的指令数 | 看指令折叠的效果 |
| CPI | 多周期指令多花的周期 | 只做函数之间的相对比较，见下 |

**用法。**
```sh
cortrace arm --platform stm32h743 --os none --profile timing --dwt-events all --probe-telnet 127.0.0.1:4444
cortrace profile run --elf fw.elf --out-dir out --iface <nic> --secs 3 --sysclk-hz 150e6 --tsgen-hz 75e6
```
`--dwt-events` 可以只开几个（`lsu,sleep`），同时会打开 `SYNCTAP`（每 2^24 个周期一个同步包），丢数据后解析器靠它找回包边界。
不加这个选项，DWT 的行为和以前完全一样。

**怎么归到函数。** 计数器绕圈的那一刻，正是第 256 个事件发生的时刻，所以这个事件就发生在当时正在跑的函数里；
每 256 个事件取一个样，统计上是无偏的。当时在哪个函数，由事件包在 ETM 字节流里的位置决定（去帧时两个流共用一个字节序号）。
报告里 `LSU%` 是"该函数的 LSU 额外周期 / 该函数的周期"。

**验证（同 §4 的 NuttX 负载，3 秒）。**

| 检查 | 结果 |
|---|---|
| SLEEP：只循环执行 WFI 的小程序，2 秒 | 1,171,962 个包 ×256 = 3.0 亿周期 = 2 秒 ×150 MHz，其他位为 0 |
| SLEEP：20% 占空的程序（忙 30 万周期，睡到下个 SysTick） | 忙 6001 万周期 + 睡 2.400 亿 = 3.00002 亿，对墙钟 6 ppm；占用率 20.0%，与设计值一致 |
| EXC 落点 | 87% 落在 `exception_common`（出栈）、`nxsched_switch`（那里的 `svc 0` 入栈）、`note_resume`（返回后），即 SVC 往返路径 |
| LSU，D-cache 开 → 关 | 访存额外周期 1250 万 → 2.38 亿；每条指令的 CPI 增加 1.38 个周期（1.47 → 2.85），LSU 每条指令从 0.04 增加到 1.51（+1.47） |
| 同上，分函数 | 每指令的 CPI 增量与 LSU 增量吻合：`memcpy` 2.64 对 2.79，`worker_fileio` 1.72 对 1.76，`itm_stimulus_send` 2.63 对 2.52，`fdlist_get_by_index` 1.90 对 2.02 |

缓存全开时 LSU 只占周期的 2.8%，而周期比指令数多 1.44 亿：剩下的停顿不在访存上，是取指、分支、依赖停顿。
关掉 D-cache 后 LSU 占了 53%，增加的停顿几乎全是它。

**要注意的几点。**
- **睡眠时 ETM 的周期计数不走**，DWT 的 SLEEP 计数器在走。所以 CPU 占用率是 `忙 / (忙 + 睡)`，忙是周期时钟；
  周期时钟对时间戳的偏差，也要把睡眠周期加回去再比（报告已经这样算）。没有睡眠事件时，报告写"从未睡眠（或者 SLEEP 计数器没开）"，
  两种情况无法区分。
- **有睡眠时，周期性异常（SysTick）的晚到量不测。** 核心睡眠时 ETM 的周期时钟停走，tick 之间的"间隔"不是时间，
  报告写"未测量"。时钟自检里加回去的睡眠周期只算两个时间戳之间的部分，误差在 0.01% 量级（计数器按 256 取整）。
- **位置有偏差。** ETM 把一批分支攒成一个包再发，所以事件包可能比对应的指令包早到，落在前一个函数里。
  比这个延迟更短的相邻函数会被抹匀；EXC 落点的检验说明偏差不大，但函数级的 LSU% 对很短的函数（几十个周期）只做参考。
- **CPI 计数器不是绝对的"多出的周期"。** 缓存全开时它是 2.37 亿，比周期减指令数（1.44 亿）还大，M7 双发射下它的口径不是这样；
  D-cache 关掉后它反而降到 1.07 亿。报告里用 `MC%` 列出，只用来比较函数之间的相对高低。
- 一个包是 256 次事件：事件少的函数（几十次）统计上抽不到样，LSU% 是 0 不代表真的没有。
