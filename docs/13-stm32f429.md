# STM32F429（Cortex-M4，ETMv3.5）
状态：在 STM32F429I-DISC1 上抓到并解出了完整的调用树。**2 位口能用，4 位口抓到的 trace 解不出来**（第 5 节）。
这是第一个不带 ETMv4 的目标。M4 的 ETM 是 ETMv3.5，包格式、寄存器和 M7 的 ETMv4 都不同，解码走 OpenCSD 的 ETMv3 解码器，布防走 `trace_arm.py` 里单独的 `arm_etm_v3`。
## 1. 芯片
OpenOCD 读 ROM 表（0xE00FF000）的结果：
| 块 | 基址 | 备注 |
|---|---|---|
| SCS / DWT / FPB / ITM | 0xE000E000 / 0xE0001000 / 0xE0002000 / 0xE0000000 | |
| TPIU | 0xE0040000 | |
| ETM | 0xE0041000 | ETMIDR 0x4114F250（ETMv3.5），ETMCCR 0x8C842000，ETMCCER 0x18541800 |
没有漏斗、ETF 和时间戳发生器：ETM 和 ITM 直接进 TPIU，平台文件里 `path = []`，也不写 `tsgen`。DBGMCU_CR 在 0xE0042004，IDCODE 0x20016419。
trace 脚是 PE2（TRACECLK）和 PE3 到 PE6（TRACED0 到 TRACED3），都是 AF0，要打开 SYSCFG 的 I/O 补偿单元，脚配成 very high speed。这些步骤都在 `platforms/stm32f429.toml` 的 `on_trace_start` 里。
**TRACECLK 是 HCLK/2**，数据在时钟两个沿上都变，一个 TRACECLK 周期传 8 位。HCLK 168 MHz 时是 84 MHz，板上没有串电阻和缓冲，信号质量不好，模板固件把 HCLK 降到 60 MHz（TRACECLK 30 MHz）。
## 2. 布防（ETMv3.5）
`cortrace arm --platform stm32f429` 做的事，按 ETM-M4 TRM（DDI0440C）：
1. ETMCR 的 programming 位（bit 10）写两次，等 ETMSR bit 1。
2. TRACEIDR = 2，TRIGGER = never，TraceEnable 事件（TEEVR）= always，TECR1 = 0，FIFOFULL 水位（0x028）= 8，时间戳事件 = never。
3. ETMCR = port select（bit 11），`--profile timing` 再加 bit 28（时间戳）；最后写一次不带 programming 位的值，ETM 开始输出。
M4 的 ETM 没有周期计数器，所以没有 `--cycle-time` 用的数据，`timing` 档只多出同步点上的时间戳。
`default_width = 2`，所以不给 `--width` 就按 2 位布防；FPGA 侧要同步：`cortrace fpga ctrl set-width 2`。
## 3. 模板固件
`stm32f429-etm-trace-firmware/`（GCC，只用 CMSIS，不带 HAL）：8 MHz HSE 经 PLL 到 60 MHz，循环调用 `fib(12)`、`crunch(200)`（200 次 `leaf`）、`branchy(300)` 和 `spin(200)`，PG13 的 LED 翻转。CMSIS 头文件克隆到被 git 忽略的 `Drivers/` 里。`make` 编译，`make flash` 用 OpenOCD 烧。
## 4. 抓取与解码
```sh
cortrace fpga ctrl set-width 2
cortrace fpga ctrl oversample off          # 带过采样功能的比特流才有这条
cortrace arm --platform stm32f429 --os none --probe-telnet 127.0.0.1:<port> --profile coverage
cortrace-grab <iface> 2 f429.raw 256 512
cortrace-decode f429.raw f429.nm --elf f429_trace.elf --raw --trace-width 2 \
    --etm-version 3 --etm-trace-id 2 --etm-v3-idr 0x4114F250 --etm-v3-ctrl 0x800 --etm-v3-ccer 0x18541800
```
核对：2 MB 的 ETM 字节解出 222978 次调用，全部配平，`stream health` 是 `clean`，7 个函数；每次 `work()` 里 `fib` 465 次（2·fib(13)−1）、`leaf` 200 次、`crunch`、`branchy`、`spin` 各 1 次，和源码一致。
`--etm-v3-ctrl` 要和芯片上 ETMCR 的值一致（0x800 是 port select，没开上下文 ID 和数据 trace）。
## 5. 4 位口的问题
4 位口抓到的流里，TPIU 帧里某些字节对的第二个字节丢了：半同步（`FF 7F`）出现在一个字节对的两个字节之间，后面紧跟下一对的 ID 字节。丢的字节多半落在 ETM 分支地址包的中间（形如 `c1 ?? bc`，缺了第二个字节），OpenCSD 把后面的原子包都当成地址续字节，吞到下一个 ISYNC 为止，随后报包序列错。
已经排除的原因：
- IDELAY tap 0 到 31 全部扫过，出错的比例不变（2.4%）。
- HCLK 从 60 MHz 降到 3.75 MHz（TRACECLK 30 MHz 到约 2 MHz），出错位置不变。
- 脚的驱动速度（OSPEEDR）从 very high 改到 low，没有改善。
- 同一块板、同一个固件、同一个 TPIU，只把端口宽度改成 2 位，整段流解码干净。
所以问题和采样相位、时钟频率、脚的驱动都无关，只出现在 4 位口。还没查清楚是 TRACED2/TRACED3（PE5、PE6）这两根线的连接，还是 F4 的 TPIU 在 4 位模式下的行为。2 位口的带宽（30 MHz TRACECLK 时 15 MB/s）对这个固件够用。
