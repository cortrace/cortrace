# Cortrace — 调用图、火焰图和线程统计（`stats`）
日期：2026-11-06
状态：已实现，单元测试覆盖。板上验证用的是 i.MX RT1176 上的 LVGL 抓取。H743 没接，没有在 H743 和 NuttX 上跑过，线程部分只有合成数据的测试，没有真实的多线程抓取。

> 关系：和覆盖率（`07`）、周期剖析（`08`）共用抓取、去帧和 OpenCSD 解码，在调用栈机（`CallStackMachine`）产生的切片流上多一个消费者
> （`src/callstats.cpp`）。`cortrace profile` 给每个函数的自身周期和 CPI，`stats` 给调用关系、包含时间和线程。
---
## 1. 能得到什么
| 结果 | 含义 |
|---|---|
| 每个函数的调用次数、自身周期、包含周期，每次调用包含周期的 min/p50/p90/p99/max | 热点；一个函数慢是自己慢，还是被它调用的慢 |
| 调用者→被调用者的边：次数和包含周期 | 一个函数的时间是从哪里来的、花到哪里去了（`--func`） |
| 折叠栈（每条栈的自身周期） | 火焰图的输入，也能直接导入 speedscope、`flamegraph.pl` |
| 每个线程：运行周期、被中断抢走的周期、被中断抢占的次数、切入次数、最长的一次切入到切出 | 谁占了 CPU，中断打断了谁 |
**得不到什么。** 时间来自 ETM 的周期计数，所以要用带周期计数的 profile 布防（`cortrace arm --profile timing`）；`coverage` 档位没有周期，解码器会报错退出。
看不到 cache miss、总线争用本身，只看到它们造成的停顿（同 `08` §6）。

## 2. 用法
```sh
cortrace arm --platform stm32h743 --os none --profile timing --probe-telnet 127.0.0.1:4444
cortrace capture --elf fw.elf --iface <nic> --secs 1 --sysclk-hz 150e6 --stats   # 照常出 Perfetto，另写 stats_<tag>.json 和 folded_<tag>.txt
cortrace stats report stats_<tag>.json                      # 线程表、函数表（按自身周期）
cortrace stats report stats_<tag>.json --sort incl --top 40 --edges 20 --unit us
cortrace stats report stats_<tag>.json --func lv_draw_sw_blend    # 谁调用它、它调用谁、各占多少
cortrace stats flame folded_<tag>.txt -o flame.svg --sysclk-hz 150e6    # 用浏览器打开，悬停看数字
```
- `--stats` 只给 `capture` 加了两个解码器选项，Perfetto 的输出不变。底层是 `cortrace-decode --stats-out stats.json --folded-out out.folded`，已有的抓取文件用 `--raw-in` 重新解码即可。
- 线程名来自 `--os` 插件和线程切换（和 Perfetto 的 Threads 轨道同一来源）；没有线程信息时只有一个线程，叫 `main`。
- `--unit us` 需要文件里记着 CPU 频率：抓取时给 `--sysclk-hz`（`capture` 默认 150 MHz，换了芯片要自己给）。
- 火焰图里一个框的宽度是这条栈的自身周期，高度是调用深度。递归很深的代码（LVGL 的对象树）会让图很高，`--min-pct` 去掉太窄的框。
- 文件格式：`format: cortrace-callstats`，`version: 1`，时间单位是周期。

## 3. 怎么算的
**时间轴。** 调用栈机给每个开始/结束事件记一个周期时钟。这个时钟只在周期计数包到达时才前进，所以一个窗口（两个计数包之间）里的所有事件时钟相同，短函数的时长会是零。
统计用的是估计值 `cycle_est`：一个计数包的周期，按窗口里已执行的指令数摊到每个事件上（和 `profile` 摊周期的方法一致）。窗口的末尾没有后继计数包时（trace 尾部），事件放在最后一个已知的时钟。
**一个调用的时间。** 只算它所在的上下文真正在运行的时间：
- 另一个线程在跑的时间不算（线程被切走又切回来，中间的时间不进它的函数）；
- 中断抢占的时间不算（中断有自己的栈，从被抢占的线程里扣掉，嵌套中断也各算各的）。
**自身周期** = 包含周期 − 被调用者（trace 完整的那些）的包含周期。
**递归。** 一个调用只把"没有被同函数的完整嵌套调用已经算过"的那部分加进函数和边的包含总数，所以总数是这个函数在栈上的时间，只算一次；一个函数的各条入边加起来等于它的总数。`min/max/百分位`描述每一次调用。
**trace 丢了数据。** 解码器报出的 `NoSync`、`TraceOn`、`AddrNacc`、`Overflow` 都记为一次丢失，每个事件带着"到此为止丢了几次"。
- 开始和结束之间丢过数据的调用，单独计数（`crossed`），不加时间；
- 两个事件之间丢过数据，这段周期不算给任何人，计入 `dropped`；
- 因为 trace 结束（或离开启动上下文）被调用栈机补上结束的调用，计入 `truncated`，不加时间。
报告头部给出这几个数。丢得多的抓取里，`dropped` 会比 `observed` 还大，这时的函数排序只能参考。

## 4. 验证
**机理**：合成切片流的单元测试覆盖嵌套、中断抢占、嵌套中断、线程切换、丢数据、截断、递归、百分位和输出格式（`tests/test_callstats.cpp`，`python/tests/test_stats.py`）。
**和 `cortrace profile` 对照**（i.MX RT1176，LVGL 连续重绘，CPU 15.6 MHz，抓 0.3 s，trace 干净、没有丢数据；两边用同一份原始抓取、同一个 ELF）：
| | `cortrace-prof` | `stats` |
|---|---|---|
| 观察到的周期 | 4,664,889 | 4,658,906 |
| `lv_draw_sw_blend_image_to_rgb565` 自身周期 | 1,018,228 | 1,018,260 |
| `lv_font_get_bitmap_fmt_txt` | 293,108 | 293,129 |
| `get_prop_core` | 326,434 | 327,146 |
| `lv_color_16_16_mix` | 324,431 | 331,611 |
| `lv_draw_sw_blend_color_to_rgb565` | 846,575 | 822,874 |
- 123 个函数（自身周期超过 1000）的差异合计占 3.5%（把别名函数 `memset`/`lv_memset` 合起来算之后）。
- 这两个名字是同一个地址的别名，两边挑的名字不同：分开看差 −99% 和 +151%，合起来 160,654 对 160,627。
- 自身周期超过 20,000 的 26 个函数里，25 个差在 3% 以内；一个例外是 `lv_text_get_next_line.part.0`，差 −54%（48,178 对 22,335）。我没有查原因，猜是尾调用：调用栈机在尾调用时把栈顶改名，整个帧的时间记在帧开始时的名字下，`profile` 按地址记。
- 不变量在真实数据上都成立：没有函数的自身周期大于包含周期，所有包含周期都不超过观察到的总周期，每个函数的入边之和等于它的包含周期。
- 在有丢数据的抓取上（RT1176，53 MHz 引脚时钟，0.3 s，3.6 万次丢失）：只有 36% 的周期可以放到某个调用上，`crossed` 的调用有 17,164 个，不变量同样成立。

## 5. 局限
- **精度**：周期计数的阈值是 16 个周期（`TRCCCCTLR`），按指令数摊开之后，单个调用的时长仍是估计，几十个周期以内的短函数，单次调用的数不可靠；累计的自身周期和 `profile` 一致（见上表）。
- **尾调用**：见上，被尾调用的函数的时间记在原来的名字下，`profile` 的按地址归属更准。
- **函数名**：别名地址（同一地址多个符号）选哪个名字取决于符号表，两个工具可能不同。
- **线程**：线程切换的位置按 ETM 字节粒度对齐，会偏一点；只有 NuttX 的插件能给线程名，其他系统是 `thread <指针折叠值>`；没有在真实的多线程抓取上验证过。
- **ISR**：中断的栈按异常号分轨道，中断里的函数的路径以 `IRQ:名字` 开头，不挂在被抢占的线程下面；火焰图里中断单独一棵。
- **内存**：切片流整个放在内存里（和 Perfetto 输出一样），不像 `cover stream` 那样流式处理；一次抓取别太长。
- **没做的**：MC/DC、决策覆盖不在这里；任务的优先级反转、调度延迟（切出到切入）这类需要 RTOS 对象信息的统计也没做。
